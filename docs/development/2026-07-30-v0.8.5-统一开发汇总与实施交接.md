## 4. rolling_batch产品机制

以下是`scope_mode: rolling_batch`的默认策略，不是整个插件不可覆盖的全局常量。

项目规格可以显式覆盖`batch_size`、目标时长、镜头数和初始来源窗口；未声明时使用本节默认值。

### 4.1 默认批次规则

- `batch_size`默认3集；
- `target_duration_seconds`默认60秒；
- 时长容差默认±10%，即54-66秒；
- 每集建议12-18个分镜；
- 同一已确认批次连续完成，中间不询问；
- 整批完成并通过验收后停止；
- 只有用户确认后才能定义下一批；
- 全剧最终集数可以未知。

### 4.2 默认3章滚动来源窗口

`initial_source_window_units`默认3章。三章只是初始分析窗口，不是必须消耗范围。

```text
读取当前窗口
→ 提取完整事件
→ 评估能否支撑当前已确认批次
→ 足够：停止扩窗并保留剩余事件
→ 不足：只继续读取相邻新章节
```

### 4.3 内容过剩

如果第1章已经足够支撑E001-E003：

- 当前批次只使用实际能够承载的事件；
- 第1章未使用事件、第2章和第3章进入carryover；
- B02优先使用carryover；
- 不重复分析第1-3章；
- 不为消耗已分析内容强行压缩剧情。

### 4.4 内容不足

如果第1-3章只够支撑1集：

- 根据实际缺口继续读取相邻章节；
- 新增章节只做增量分析；
- 达到当前批次所需后立即停止；
- 不顺势扫描或分析全书。

### 4.5 跨章事件

如果关键事件跨越当前窗口结尾：

- 允许读取下一章的直接相关内容；
- 读到事件结果或合理悬念切点即停止；
- 边界探针不自动进入当前批次；
- 探针读取范围和原因必须写入运行记录。

## 5. 禁止循环重复读取和重复分析

这是v0.8.5必须新增的机器级契约。要称为“机器级”，生产来源I/O必须经过受控命令；仅在Skill里写提示词不能视为完成。

### 5.1 必须新增或正式化的生产入口

至少提供以下等价能力，名称可以按现有CLI风格调整：

```text
ingest-source
plan-rolling-source-window
register-source-analysis
consume-source-events
```

要求：

- Word标准化、章节切分、分析登记和事件消费都有唯一可审计入口；
- 每个命令明确是否写状态；
- 写状态由主任务单一写入者完成；
- 子代理只写主任务指定的项目内绝对路径；
- 绕过受控入口的直接生产写入不得被登记为有效制品。

### 5.2 Word全文只技术提取一次

- 原始Word只执行一次标准化正文提取和章节切分；
- 记录原始文件绝对路径、文件SHA256、大小和提取器版本；
- 每章登记`source_unit_id + content_sha256`；
- 原文件哈希未变化时，后续批次不得重新解包、重新切分或重新扫描Word全文；
- 后续使用标准化章节文件和已登记的来源分析制品。

如果原始文件哈希变化：

1. 不直接覆盖旧登记；
2. 创建新来源版本；
3. 计算受影响章节；
4. 只使受影响分析和下游制品失效。

### 5.3 每章完整语义分析最多一次

- 相同`source_unit_id + content_sha256 + analysis_contract_version`只允许一个当前有效分析版本；
- 已经分析的章节不得再次创建来源分析智能体；
- 新批次直接复用事件、对白原子、状态和来源定位；
- 分片规划器创建任务前必须剔除已有有效分析的章节；
- 并发重试必须使用同一幂等键，不能产生两个有效版本。

### 5.4 允许的局部核对

只有以下情况可以读取少量原文：

- 按段落ID核对一句对白；
- 核对事件开始和结束；
- 对下一未分析章节执行边界探针；
- 用户纠正原著；
- 原始文件哈希变化。

局部核对必须记录：

- 原因；
- `source_unit_id`；
- locator范围；
- 读取者；
- 时间；
- 是否产生状态变化。

局部核对不得重新读取整章或全文。

### 5.5 必须新增的正式制品

必须新增并登记：

```text
rolling_source_progress
chapter_analysis_registry
```

`chapter_analysis_registry`至少记录：

- `source_unit_id`；
- `content_sha256`；
- `analysis_contract_version`；
- 分析制品路径、版本和hash；
- `analysis_status`：`pending/analyzed/invalidated`；
- `analyzed_at`；
- 幂等键。

`rolling_source_progress`至少记录：

- 当前批次ID；
- `analyzed_source_unit_ids`；
- `carryover_event_ids`；
- `next_read_start`；
- 每个事件的`unconsumed/partially_consumed/consumed/invalidated`状态；
- 事件与已交付剧集的绑定；
- 最近一次窗口扩展原因。

`analyzed_through`和`consumed_through`可以作为派生摘要，但不能代替逐章节、逐事件状态，因为动态窗口可能存在局部探针和非连续消费。

### 5.6 必须实现的阻断码

- `source_unit_reanalysis_forbidden`
- `full_source_rescan_forbidden`
- `analysis_registry_hash_mismatch`
- `carryover_analysis_missing`
- `source_ingest_version_conflict`
- `source_analysis_idempotency_conflict`

## 7. 真实报错与canonical entity ID修复

### 7.1 报错演变记录

首次确认`source_event_index`时同时出现：

### 7.2 当前剩余错误

```text
event_entity_id_invalid × 5
```

错误实体：

```text
L001
L002
L003
L004
L005
```

### 7.3 根因

当前schema v2正则只接受：

```text
C001
CHAR-...
LOC-...
PROP-...
```

却不接受插件其他正式契约一直使用的：

```text
L001
P001
```

这是插件内部ID契约不一致，不是模型内容错误。

### 7.4 正确修复

按`entity_type`接受：

```text
character: C001 或 CHAR-...
location:  L001 或 LOC-...
prop:      P001 或 PROP-...
```

同时保留：

- 全局唯一；
- ID前缀与实体类型一致；
- 未知前缀拒绝；
- 长ID向后兼容；
- 错误输出包含具体`entity_id`、`entity_type`和索引。

不得把真实项目的`L001-L005`改成其他ID绕过门禁。

## 8. 项目根目录与运行隔离

B01首次运行时，三个来源智能体把分片写入父目录：

`/Users/shinchan/Desktop/小说/tmp/B01/...`

而不是指定项目目录：

`/Users/shinchan/Desktop/小说/温夜有染_AI导演项目/tmp/B01/...`

现有`safe_relative_path()`只能阻止把项目外文件登记成制品，不能阻止代理在写入阶段先把文件写错位置。v0.8.5必须增加写入前保护。

要求：

1. 项目初始化后生成唯一、绝对、规范化的`project_root`；
2. 所有临时文件和制品路径只由`project_root`派生；
3. 不使用shell cwd或父目录猜测项目根；
4. 子代理提示词由主任务写入准确的绝对输入和输出路径；
5. 主任务在派发前校验输出路径位于`project_root`；
6. 子代理结果合并前再次校验真实路径和符号链接解析结果；
7. 越界写入返回`project_output_outside_root`；

## 10. rolling_batch项目规格正式化

当前B01规格：

```json
{
  "scope_mode": "rolling_batch",
  "expected_episodes": 3,
  "batch_size": 3,
  "current_batch_id": "B01"
}
```

其中`expected_episodes: 3`只表示当前已确认范围，不应被解释为全剧最终只有3集。

### 10.1 权威模型

`project_spec`保存相对稳定的项目策略：

```json
{
  "schema_version": 2,
  "scope_mode": "rolling_batch",
  "batch_size": 3,
  "target_duration_seconds": 60,
  "initial_source_window_units": 3,
  "final_expected_episodes": null
}
```

`project_state.batches`保存经用户确认的动态批次范围：

```json
{
  "B01": {
    "batch_id": "B01",
    "episode_ids": ["E001", "E002", "E003"],
    "status": "confirmed",
    "confirmed_at": "...",
    "approval_note": "..."
  }
}
```

运行时派生而不重复持久化：

```text
confirmed_episode_ids = 所有confirmed批次episode_ids的有序并集
confirmed_episode_count = len(confirmed_episode_ids)
current_batch_episode_ids = 当前批次episode_ids
```

### 10.2 规则

- `final_expected_episodes`可以为`null`；
- rolling_batch规划和批次交付以已确认批次范围为权威；
- 全剧最终交付只有在`final_expected_episodes`明确且所有集覆盖完成后才能成立；
- B02必须在用户确认后通过受控命令定义；
- 未确认时不得创建B02；
- 不得因为B01旧规格`expected_episodes=3`而永久阻断E004；
- 也不得让未确认的新规格自动放开E004；
- 项目规格更新必须创建新版本和新文件路径，不得原地覆盖v1。

### 10.3 向后兼容

- `scope_mode: full_series`旧项目继续使用明确的`expected_episodes`；
- rolling_batch旧项目中的`expected_episodes`迁移为当前已确认批次上限，不自动转成`final_expected_episodes`；
- 当前B01根据已有确认记录迁移为`B01.status=confirmed`；
- 迁移不得重建项目、删除历史规格或重新确认已经有效确认的B01范围。

### 10.4 必须审计的消费者

不能只修改字段校验。至少检查并测试：

- `project_expected_episodes()`及其替代接口；
- `confirmed_project_spec_payload()`；
- `define-batch`；
- `validate-project`；
- `validate-handoff`；
- 批次handoff和全剧handoff；
- `build-handoff`；
- `validate-seedance`；
- 逐集交付和全剧覆盖计算；
- 所有把`expected_episodes`当成永久总集数的测试。

建议拆分接口：

```text
project_final_expected_episodes(...)
confirmed_episode_ids(...)
current_batch_episode_ids(...)
```

避免继续用一个`project_expected_episodes()`同时表达“当前已确认范围”和“全剧最终总数”。
